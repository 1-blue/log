 오늘은 대규모 프로젝트를 진행하면서 개발자들이 한 번쯤 고민해 봤을 주제, 바로 **모노레포(Monorepo) 아키텍처**에 대해 심도 있게 다뤄보려고 해요. 수많은 서비스와 라이브러리가 복잡하게 얽혀 있는 현대 웹 개발 환경에서, 어떻게 하면 효율적으로 코드를 관리하고 팀 생산성을 높일 수 있을지 함께 고민해 봐요.
 
 ## 🤔 왜 모노레포인가요?
 
 ### 0️⃣ 대규모 프로젝트의 도전 과제<br />
 프로젝트의 규모가 커지고, 여러 팀이 다양한 애플리케이션(웹, 모바일, 관리자 페이지 등)과 공유 라이브러리를 개발하게 되면, 코드 관리와 협업에 많은 어려움이 생겨요.<br />
 전통적인 방식인 **멀티레포(Multi-repo)**는 각 프로젝트를 독립적인 Git 저장소로 관리하는 방식인데요. 이는 프로젝트 간의 강한 독립성을 보장하지만, 다음과 같은 문제점들을 야기하기도 해요.
 
 ### 1️⃣ 멀티레포의 한계점<br />
 *   **복잡한 의존성 관리:** 여러 프로젝트가 공통 라이브러리를 사용할 때, 각 레포마다 라이브러리 버전을 따로 관리해야 해요. 이로 인해 버전 불일치 문제나 의존성 지옥에 빠질 위험이 커져요.<br />
 *   **코드 재사용의 어려움:** 공통으로 사용되는 UI 컴포넌트나 유틸리티 함수를 공유하기 위해 별도의 패키지를 만들고, 이를 각 레포에 배포한 후 설치해야 하는 번거로움이 있어요. 이 과정이 복잡하고 시간이 많이 소요돼요.<br />
 *   **일관성 없는 개발 환경:** 각 레포마다 ESLint, Prettier, TypeScript 설정 등이 달라질 수 있어서, 코드 스타일의 일관성을 유지하기 어렵고 개발자들의 혼란을 초래할 수 있어요.<br />
 *   **비효율적인 CI/CD:** 작은 변경 사항이라도 여러 레포에 걸쳐 있다면, 각각의 CI/CD 파이프라인을 독립적으로 실행해야 해서 빌드 및 배포 시간이 길어질 수 있어요.
 
 모노레포는 이런 멀티레포의 한계점들을 극복하고, 대규모 프로젝트를 더욱 효율적으로 관리하기 위한 강력한 대안으로 떠오르고 있어요.
 
 ## 🚀 모노레포의 장점과 단점
 
 모노레포는 모든 프로젝트 코드를 단일 Git 저장소에 저장하는 방식이에요. 마치 하나의 거대한 폴더 안에 여러 개의 작은 프로젝트 폴더가 있는 것과 같다고 생각하시면 돼요.<br />
 그럼 모노레포가 어떤 장점과 단점을 가지고 있는지 자세히 살펴볼까요?
 
 ### 0️⃣ 모노레포의 장점 👍<br />
 *   **코드 공유 및 재사용성 극대화:** 공통 UI 컴포넌트, 유틸리티 함수, 타입 정의 등을 쉽게 공유하고 재사용할 수 있어요. 별도의 배포 과정 없이 내부 패키지 의존성으로 바로 연결할 수 있어서 개발 속도가 빨라져요.<br />
 *   **단일화된 의존성 및 버전 관리:** 모든 프로젝트가 하나의 `package.json` 또는 워크스페이스 설정을 공유하여 의존성 버전을 일관되게 관리할 수 있어요. 특정 라이브러리를 업데이트할 때 모든 프로젝트에 걸쳐 한 번에 반영할 수 있죠.<br />
 *   **간결한 CI/CD 파이프라인:** 변경된 파일이 포함된 패키지만 빌드, 테스트, 배포하도록 최적화할 수 있어요. 이는 CI/CD 시간을 크게 단축시키고 리소스 낭비를 줄여줘요.<br />
 *   **개발 환경 설정 간소화:** ESLint, Prettier, TypeScript 등 공통 개발 도구 설정을 루트 레벨에서 한 번만 설정하면 모든 서브 프로젝트에 적용할 수 있어요. 개발자 온보딩이 훨씬 쉬워진답니다.<br />
 *   **전체 프로젝트 가시성 증대:** 모든 코드가 한곳에 모여 있어서, 다른 팀의 프로젝트나 공유 라이브러리 코드를 쉽게 탐색하고 이해할 수 있어요. 이는 팀 간의 협업과 지식 공유를 촉진해요.<br />
 *   **리팩토링 용이성:** 공통 라이브러리의 함수 시그니처가 변경되었을 때, 영향을 받는 모든 프로젝트에서 즉시 변경 사항을 확인하고 수정할 수 있어서 대규모 리팩토링이 훨씬 안전하고 효율적이에요.
 
 ### 1️⃣ 모노레포의 단점 👎<br />
 *   **초기 설정 복잡성:** 모노레포 툴(Lerna, Nx, Turborepo, Yarn/pnpm Workspaces 등)의 학습과 설정에 초기 비용이 발생할 수 있어요. 적절한 툴을 선택하고 워크스페이스를 구성하는 데 시간이 필요하죠.<br />
 *   **빌드 시간 증가 가능성:** 만약 모노레포 툴의 최적화 기능을 제대로 활용하지 못하면, 모든 프로젝트를 매번 빌드하게 되어 전체 빌드 시간이 길어질 수 있어요.<br />
 *   **코드베이스 규모 증가:** 단일 저장소에 모든 코드가 모여 있기 때문에, 저장소의 크기가 매우 커질 수 있어요. 이는 Git 작업(clone, fetch)이나 IDE 성능에 영향을 줄 수도 있어요.<br />
 *   **심리적 부담:** 모든 코드가 한곳에 있다는 점이 개발자들에게 심리적인 부담감이나 혼란을 줄 수도 있어요. 코드베이스가 너무 방대하게 느껴질 수 있죠.<br />
 *   **특정 툴에 대한 의존성:** 모노레포를 효율적으로 관리하기 위해서는 전용 툴에 대한 의존성이 생겨요. 툴이 제공하는 기능과 제약 사항을 이해하고 따라야 하죠.
 
 모노레포는 만능 해결책이 아니에요. 프로젝트의 규모, 팀의 역량, 기술 스택 등을 고려하여 신중하게 도입 여부를 결정해야 해요.
 
 ## ⚙️ 모노레포, 어떻게 설계해야 할까요?
 
 모노레포를 성공적으로 도입하기 위해서는 체계적인 설계가 필수적이에요. 핵심은 각 프로젝트와 라이브러리를 논리적으로 분리하고, 이들을 효과적으로 연결하는 구조를 만드는 것이랍니다.
 
 ### 0️⃣ 핵심 아이디어: 패키지(Packages) 분리 📦<br />
 모노레포의 가장 기본적인 원칙은 각 애플리케이션(예: 웹 앱, 관리자 앱, 백엔드 API)과 공유 가능한 라이브러리(예: UI 컴포넌트, 유틸리티 함수, 타입 정의)를 독립적인 패키지로 분리하는 거예요. 각 패키지는 자체적인 `package.json` 파일을 가지며, 서로 의존성을 가질 수 있어요.
 
 ### 1️⃣ 디렉토리 구조 설계 📁<br />
 일반적으로 모노레포는 `apps/`와 `packages/`라는 두 개의 최상위 디렉토리를 사용하는 경우가 많아요.
 
 *   `apps/`: 실제 사용자에게 서비스되는 애플리케이션들을 모아두는 곳이에요. Next.js 웹 앱, React 관리자 앱, Express/NestJS 기반의 백엔드 API 등이 여기에 포함될 수 있어요.<br />
 *   `packages/`: 여러 애플리케이션에서 공유되는 라이브러리들을 모아두는 곳이에요. UI 컴포넌트 라이브러리, 공통 유틸리티 함수, 타입 정의, 설정 파일(ESLint, Prettier 등) 등이 여기에 해당돼요.
 
 ```
 root
 ├── apps
 │   ├── web            # Next.js/React 기반의 사용자 웹 애플리케이션
 │   ├── admin          # Next.js/React 기반의 관리자 웹 애플리케이션
 │   └── api            # Express/NestJS 기반의 백엔드 API
 ├── packages
 │   ├── ui             # 공통 UI 컴포넌트 라이브러리
 │   ├── utils          # 공통 유틸리티 함수 모음
 │   ├── types          # 공통 TypeScript 타입 정의
 │   └── config         # ESLint, Prettier, TypeScript 등 공통 설정 파일
 ├── .gitignore
 ├── package.json       # 모노레포 워크스페이스 설정 및 공통 스크립트
 └── pnpm-workspace.yaml # pnpm 워크스페이스 설정 파일 (또는 lerna.json, .yarnrc.yml)
 ```
 
 ### 2️⃣ 적절한 모노레포 툴 선택 🛠️<br />
 모노레포를 효율적으로 관리하려면 워크스페이스 기능을 제공하는 패키지 매니저나 전용 툴이 필요해요. 대표적인 툴들은 다음과 같아요.
 
 *   **Yarn Workspaces / pnpm Workspaces:** 패키지 매니저 자체에서 제공하는 워크스페이스 기능이에요. 비교적 가볍고 설정이 간단하여 시작하기 좋아요. 특히 pnpm은 하드 링크를 사용하여 디스크 공간을 절약하고 설치 속도가 빠르다는 장점이 있어요.<br />
 *   **Lerna:** 워크스페이스 관리, 버전 관리, 패키지 배포 등을 도와주는 툴이에요. Yarn/pnpm Workspaces와 함께 사용하면 시너지를 낼 수 있어요.<br />
 *   **Nx (Nrwl Extensible Dev Tools):** 빌드 시스템, 코드 생성기, 의존성 그래프 분석 등 강력한 기능을 제공하는 풀스택 모노레포 솔루션이에요. 대규모 엔터프라이즈 환경에 적합해요.<br />
 *   **Turborepo:** Nx와 유사하게 고성능 빌드 시스템과 캐싱 기능을 제공해요. 증분 빌드(incremental build)와 원격 캐싱(remote caching)을 통해 빌드 시간을 획기적으로 단축시켜줘요.
 
 각 툴마다 장단점이 명확하므로, 프로젝트의 규모, 팀의 숙련도, 필요한 기능 등을 고려하여 신중하게 선택하는 것이 중요해요. 이 글에서는 설정이 비교적 간단하고 효율적인 **pnpm Workspaces**를 예시로 보여드릴게요.
 
 ## 🛠️ 실전 모노레포 구축 예시
 
 이제 pnpm Workspaces를 활용해서 간단한 모노레포를 구축해보고, 공유 UI 컴포넌트를 사용하는 방법을 알아봐요. Next.js 앱과 React UI 라이브러리를 예시로 들어볼게요.
 
 ### 0️⃣ pnpm Workspaces를 이용한 기본 설정<br />
 먼저 루트 디렉토리를 생성하고 `pnpm init`으로 `package.json`을 만든 후, `pnpm-workspace.yaml` 파일을 생성해 워크스페이스를 설정해 줘야 해요.
 
 ```bash showLineNumbers
 # 모노레포 루트 디렉토리 생성
 mkdir my-monorepo-example
 cd my-monorepo-example
 
 # package.json 초기화
 pnpm init
 
 # apps/ 와 packages/ 디렉토리 생성
 mkdir apps packages
 
 # apps/web (Next.js 앱) 생성
 cd apps
 pnpm create next-app web --ts --eslint --tailwind --app --src-dir --use-pnpm --no-import-alias
 cd ..
 
 # packages/ui (React 컴포넌트 라이브러리) 생성
 cd packages
 mkdir ui
 cd ui
 pnpm init
 # (나중에 React, TypeScript 의존성 추가 예정)
 cd ../..
 
 # pnpm-workspace.yaml 파일 생성
 touch pnpm-workspace.yaml
 ```
 
 ### 1️⃣ `pnpm-workspace.yaml` 설정 📝<br />
 `pnpm-workspace.yaml` 파일에 워크스페이스에 포함될 패키지들의 경로를 지정해 주세요. `apps/*`는 `apps` 디렉토리 하위의 모든 디렉토리를 패키지로 인식하겠다는 의미예요.
 
 ```yaml showLineNumbers
 packages:
   - 'apps/*'
   - 'packages/*'
 ```
 
 ### 2️⃣ 루트 `package.json` 설정 📄<br />
 루트 `package.json`에는 모노레포 전체에 적용되는 스크립트나 개발 의존성(예: TypeScript)을 추가할 수 있어요. `private: true`는 이 루트 프로젝트가 직접 배포되지 않음을 의미해요.
 
 ```json showLineNumbers {5-9, 11}
 {
   "name": "my-monorepo",
   "version": "1.0.0",
   "private": true,
   "scripts": {
     "build": "pnpm --filter \"./apps/**\" build",
     "dev": "pnpm --filter \"./apps/**\" dev",
     "lint": "pnpm --filter \"./**\" lint"
   },
   "devDependencies": {
     "typescript": "^5.x.x"
   }
 }
 ```
 
 ### 3️⃣ `packages/ui` 패키지 설정 🎨<br />
 `packages/ui`는 React 컴포넌트를 담을 라이브러리 패키지예요. 여기에 `react`와 `typescript` 관련 의존성을 추가하고, `main`과 `types` 필드를 설정해 주세요.
 
 ```json showLineNumbers {3-4, 8-12}
 {
   "name": "@my-monorepo/ui",
   "version": "1.0.0",
   "main": "./src/index.ts",
   "types": "./src/index.ts",
   "license": "MIT",
   "scripts": {
     "lint": "eslint src"
   },
   "devDependencies": {
     "@types/react": "^18.x.x",
     "@types/react-dom": "^18.x.x",
     "react": "^18.x.x",
     "eslint": "^8.x.x"
   }
 }
 ```
 
 ### 4️⃣ `packages/ui`에 Button 컴포넌트 생성 ✨<br />

 ## 💡 모노레포, 성공적인 도입을 위한 팁
 
 모노레포는 강력한 도구이지만, 제대로 활용하지 못하면 오히려 복잡성을 증가시킬 수 있어요. 성공적인 모노레포 도입을 위한 몇 가지 팁을 알려드릴게요.
 
 *   **점진적 도입 고려:** 모든 프로젝트를 한 번에 모노레포로 전환하기보다는, 신규 프로젝트부터 시작하거나 기존 레거시 시스템에 점진적으로 적용하는 것을 고려해 보세요. 작은 성공 경험을 통해 팀의 숙련도를 높이는 것이 중요해요.<br />
 *   **적절한 툴 선택:** 팀의 규모, 기술 스택, 요구사항(강력한 빌드 캐싱, 코드 생성, 의존성 그래프 분석 등)에 가장 적합한 모노레포 툴을 신중하게 선택해야 해요. Nx나 Turborepo 같은 고성능 툴은 초기 학습 곡선이 있지만, 대규모 프로젝트에서 큰 이점을 제공할 수 있어요.<br />
 *   **명확한 패키지 경계:** 각 패키지의 역할과 책임을 명확하게 정의하고, 패키지 간의 의존성 규칙을 설정해 주세요. 순환 의존성(circular dependency)을 피하고, 응집도 높은 패키지를 설계하는 것이 중요해요.<br />
 *   **CI/CD 최적화:** 모노레포 툴이 제공하는 증분 빌드(incremental build) 및 캐싱 기능을 적극적으로 활용하여, 변경된 패키지에만 빌드, 테스트, 배포가 이루어지도록 CI/CD 파이프라인을 최적화해야 해요. 이는 빌드 시간을 획기적으로 단축시켜줘요.<br />
 *   **철저한 문서화:** 모노레포의 구조, 각 패키지의 역할, 툴 사용법, 기여 가이드 등을 상세하게 문서화해 주세요. 새로운 팀원이 합류하거나 프로젝트를 이해하는 데 큰 도움이 될 거예요.<br />
 *   **코드 컨벤션 통일:** ESLint, Prettier, Stylelint 등의 린터와 포맷터를 루트 레벨에서 설정하여 모든 패키지의 코드 스타일 일관성을 유지해 주세요. 이는 코드 리뷰를 용이하게 하고 코드 품질을 높이는 데 기여해요.
 
 ## 📝 정리
 
 오늘은 모노레포 아키텍처에 대해 깊이 있게 탐구해 봤어요. 모노레포는 대규모 프로젝트에서 코드 재사용성을 극대화하고, 의존성 관리를 단순화하며, CI/CD 효율성을 높이는 강력한 아키텍처 패턴이에요.<br />
 
 초기 설정 비용과 학습 곡선이 존재하지만, 장기적으로는 팀 생산성과 프로젝트 유지보수성을 크게 향상시킬 수 있는 잠재력을 가지고 있어요. 프로젝트의 특성과 팀의 상황을 고려하여 현명하게 모노레포를 도입하고, 위에 제시된 팁들을 활용하여 성공적인 개발 경험을 만들어 나가시길 바라요.<br />
 
 이 포스팅이 초중급 개발자분들께 모노레포에 대한 이해를 돕고, 실무에 적용하는 데 실질적인 도움이 되었으면 좋겠어요. 궁금한 점이 있다면 언제든지 질문해 주세요!
