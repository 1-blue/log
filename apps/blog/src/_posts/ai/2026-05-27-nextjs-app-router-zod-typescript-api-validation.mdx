오늘은 Next.js App Router 환경에서 API를 개발할 때, Zod와 TypeScript를 활용해서 데이터 유효성 검사와 타입 안전성을 동시에 확보하는 방법에 대해 이야기해 보려고 해요.

## 🤔 문제/배경

### 0️⃣ 왜 API 유효성 검사가 중요한가요?

웹 애플리케이션에서 사용자 입력이나 외부 시스템으로부터 데이터를 받을 때, 이 데이터가 우리가 예상하는 형식이 아닐 수 있어요.<br />
예를 들어, 숫자여야 할 필드에 문자열이 들어오거나, 필수 필드가 누락될 수도 있죠.<br />
이런 유효하지 않은 데이터가 백엔드로 전달되면, 다음과 같은 문제들이 발생할 수 있어요.<br />

- **데이터 무결성 손상**: 잘못된 데이터가 데이터베이스에 저장될 수 있어요.<br />
- **보안 취약점**: 악의적인 입력으로 SQL Injection이나 XSS(Cross-Site Scripting) 같은 공격에 노출될 수 있어요.<br />
- **서버 에러**: 예상치 못한 데이터 형식으로 인해 서버 로직에서 런타임 에러가 발생할 수 있어요.<br />
- **사용자 경험 저하**: 잘못된 입력에 대한 명확한 피드백 없이 에러가 발생하면 사용자들은 혼란스러워할 거예요.<br />

그렇기 때문에 API 요청 데이터에 대한 철저한 유효성 검사는 안정적이고 안전한 서비스를 만드는 데 필수적인 요소라고 할 수 있어요.

### 1️⃣ 기존 방식의 한계: 수동 검사와 타입 불일치

기존에는 API 요청 데이터를 검증할 때 다음과 같은 방식들을 주로 사용했어요.<br />

- **수동 검사**: `if/else` 문을 사용해서 각 필드를 직접 검사하는 방식이에요. 코드가 길어지고 유지보수가 어려워지며, 휴먼 에러의 가능성이 높아요.<br />
- **라이브러리 사용 (런타임 검사만)**: `validator.js` 같은 라이브러리를 사용해서 런타임에 데이터 유효성을 검사할 수 있어요. 하지만 TypeScript 환경에서는 이 라이브러리가 제공하는 검증 로직과 코드의 타입 정의가 별개로 관리되어 타입 불일치 문제가 생길 수 있어요.<br />
- **TypeScript 인터페이스/타입**: TypeScript로 데이터의 형태를 정의하면 개발 시점에 타입 안전성을 확보할 수 있지만, 이는 컴파일 시점에만 유효해요. 실제 런타임에 들어오는 데이터는 TypeScript의 감시를 벗어나기 때문에, 런타임 유효성 검사는 별도로 필요해요.<br />

이러러한 방식들은 런타임 유효성 검사와 개발 시점의 타입 안전성을 동시에 효과적으로 확보하기 어렵다는 한계가 있어요. 특히 Next.js App Router의 Route Handler에서는 클라이언트로부터 HTTP 요청을 받아 처리하기 때문에, 이 문제를 더욱 효율적으로 해결해야 할 필요가 있어요.

## ⚙️ Zod와 TypeScript로 해결하기

### 0️⃣ Zod란 무엇이고 왜 사용할까요?

Zod는 TypeScript 우선(TypeScript-first) 스키마 선언 및 유효성 검사 라이브러리예요.<br />
Zod의 가장 큰 장점은 **런타임 유효성 검사와 동시에 TypeScript 타입 추론을 제공**한다는 점이에요.<br />
즉, Zod 스키마를 한 번 정의하면 런타임에 데이터 유효성을 검사할 수 있을 뿐만 아니라, 그 스키마로부터 파생된 TypeScript 타입을 자동으로 얻을 수 있어서 타입 안전성까지 보장받을 수 있어요.<br />

Zod를 사용하면 다음과 같은 이점들을 얻을 수 있어요.<br />

- **단일 소스**: 유효성 검사 로직과 타입 정의를 한 곳에서 관리할 수 있어요.<br />
- **강력한 타입 추론**: 복잡한 스키마에서도 정확한 TypeScript 타입을 자동으로 생성해 줘요.<br />
- **읽기 쉬운 API**: 직관적인 메서드 체이닝으로 스키마를 쉽게 정의할 수 있어요.<br />
- **커스터마이징 가능**: 에러 메시지나 커스텀 유효성 검사 로직을 쉽게 추가할 수 있어요.<br />

### 1️⃣ 스키마 정의와 타입 추론

Zod 스키마는 객체, 문자열, 숫자, 배열 등 다양한 데이터 타입을 지원하며, 각 타입에 대한 상세한 규칙을 정의할 수 있어요.<br />

간단한 사용자 스키마를 예시로 살펴볼까요?

```ts showLineNumbers
import { z } from "zod";

// 1. Zod 스키마 정의
const userSchema = z.object({
  id: z.string().uuid("유효한 UUID 형식이어야 해요.").optional(),
  name: z
    .string()
    .min(2, "이름은 최소 2글자 이상이어야 해요.")
    .max(50, "이름은 50글자를 넘을 수 없어요."),
  email: z.string().email("유효한 이메일 주소여야 해요."),
  age: z
    .number()
    .int("나이는 정수여야 해요.")
    .min(0, "나이는 0보다 작을 수 없어요.")
    .optional(),
  roles: z.array(z.enum(["admin", "user", "guest"])).default(["user"]),
  isActive: z.boolean().default(true),
  createdAt: z.date().default(() => new Date()),
});

// 2. 스키마로부터 TypeScript 타입 추론
type User = z.infer<typeof userSchema>;

// 예시 사용
const validUser: User = {
  name: "블루",
  email: "blue@example.com",
  age: 30,
  roles: ["admin", "user"],
  isActive: true,
  createdAt: new Date(),
};

const newUser: User = {
  name: "새로운 사용자",
  email: "new@example.com",
}; // age, roles, isActive, createdAt는 default 값으로 자동 추론돼요.

console.log(validUser);
console.log(newUser);
```

위 코드에서 `z.object`를 사용하여 객체 스키마를 정의했어요.<br />
각 필드에 대해 `string()`, `number()`, `array()`, `boolean()`, `date()` 등의 Zod 타입을 지정하고, `min()`, `max()`, `email()`, `uuid()`, `int()`, `optional()`, `default()`와 같은 유효성 검사 메서드를 체이닝해서 상세 규칙을 추가했어요.<br />
특히 `z.infer<typeof userSchema>`를 사용하면, 이 스키마로부터 TypeScript `User` 타입을 자동으로 추론할 수 있다는 점이 핵심이에요. 덕분에 API 요청 데이터를 검증하고 나면, 해당 데이터는 `User` 타입으로 안전하게 사용할 수 있게 되는 거죠.

## 🚀 Next.js App Router에 적용하기

### 0️⃣ Route Handler에서 Zod 스키마 활용

Next.js App Router의 Route Handler는 서버에서 동작하는 API 엔드포인트를 쉽게 만들 수 있게 해줘요.<br />
여기서 Zod를 활용하면, 들어오는 요청(Request)의 `body`나 `query` 파라미터 등을 효과적으로 검증할 수 있어요.<br />

```tsx showLineNumbers
// app/api/users/route.ts
import { NextResponse } from "next/server";
import { z } from "zod";

// 사용자 생성 요청에 대한 스키마 정의
const createUserSchema = z.object({
  name: z.string().min(2, "이름은 최소 2글자 이상이어야 해요."),
  email: z.string().email("유효한 이메일 주소여야 해요."),
  password: z.string().min(8, "비밀번호는 최소 8자 이상이어야 해요."),
});

// 스키마로부터 타입 추론
type CreateUserPayload = z.infer<typeof createUserSchema>;

export async function POST(request: Request) {
  try {
    const body: CreateUserPayload = await request.json();

    // Zod 스키마로 요청 본문 유효성 검사
    // .parse()는 유효성 검사에 실패하면 에러를 던져요.
    // .safeParse()는 에러를 던지지 않고 결과 객체를 반환해요.
    const validatedData = createUserSchema.parse(body);

    // 유효성 검사를 통과한 데이터는 CreateUserPayload 타입으로 안전하게 사용 가능해요.
    console.log("유효한 사용자 데이터:", validatedData);

    // 실제 데이터베이스 저장 로직 등...
    // const newUser = await db.user.create({ data: validatedData });

    return NextResponse.json(
      {
        message: "사용자가 성공적으로 생성되었어요.",
        user: { name: validatedData.name, email: validatedData.email }, // 비밀번호는 응답에 포함하지 않아요.
      },
      { status: 201 },
    );
  } catch (error) {
    if (error instanceof z.ZodError) {
      // Zod 유효성 검사 에러 처리
      return NextResponse.json(
        {
          message: "유효성 검사 실패했어요.",
          errors: error.errors.map((err) => ({
            path: err.path.join("."),
            message: err.message,
          })),
        },
        { status: 400 },
      );
    }
    console.error("API 에러 발생:", error);
    return NextResponse.json(
      { message: "서버 에러가 발생했어요." },
      { status: 500 },
    );
  }
}
```

위 `POST` Route Handler 예시에서는 `createUserSchema.parse(body)`를 통해 들어온 요청 본문을 검증하고 있어요.<br />
만약 유효성 검사에 실패하면 `z.ZodError`가 발생하고, 이를 `catch` 블록에서 잡아 사용자에게 친절한 에러 메시지를 반환할 수 있어요.<br />
`validatedData`는 `CreateUserPayload` 타입으로 추론되므로, 이후 코드에서는 이 데이터를 타입 안전하게 사용할 수 있답니다.

### 1️⃣ 커스텀 유효성 검사 미들웨어 만들기

코드 중복을 줄이고 싶다면, Zod 유효성 검사를 수행하는 커스텀 유틸리티 함수나 미들웨어 패턴을 만들 수 있어요.<br />
이를 통해 여러 Route Handler에서 동일한 검사 로직을 재사용할 수 있답니다.<br />

먼저 `lib/validation.ts` 같은 파일에 유효성 검사 유틸리티를 만들어 볼게요.

```ts showLineNumbers
// lib/validation.ts
import { z, ZodSchema } from "zod";
import { NextResponse } from "next/server";

type ValidationResult<T> =
  | { success: true; data: T }
  | { success: false; error: z.ZodError };

export function validate<T>(
  schema: ZodSchema<T>,
  data: any,
): ValidationResult<T> {
  const result = schema.safeParse(data);
  if (result.success) {
    return { success: true, data: result.data };
  } else {
    return { success: false, error: result.error };
  }
}

// Route Handler에서 사용할 수 있는 유틸리티 함수
export async function validateRequest<T>(
  request: Request,
  schema: ZodSchema<T>,
) {
  try {
    const body = await request.json();
    const validationResult = validate(schema, body);

    if (validationResult.success) {
      return { success: true, data: validationResult.data };
    } else {
      return {
        success: false,
        errorResponse: NextResponse.json(
          {
            message: "유효성 검사 실패했어요.",
            errors: validationResult.error.errors.map((err) => ({
              path: err.path.join("."),
              message: err.message,
            })),
          },
          { status: 400 },
        ),
      };
    }
  } catch (error) {
    console.error("요청 본문 파싱 에러 또는 기타 에러:", error);
    return {
      success: false,
      errorResponse: NextResponse.json(
        { message: "잘못된 요청 형식이에요." },
        { status: 400 },
      ),
    };
  }
}
```

이제 이 `validateRequest` 유틸리티를 Route Handler에서 활용해볼까요?<br />

```tsx showLineNumbers {1,9-16,28}
// app/api/products/route.ts
import { NextResponse } from "next/server";
import { z } from "zod";
import { validateRequest } from "@/lib/validation"; // 위에서 만든 유틸리티 임포트

// 상품 생성 요청에 대한 스키마 정의
const createProductSchema = z.object({
  name: z.string().min(3, "상품명은 최소 3글자 이상이어야 해요."),
  price: z
    .number()
    .positive("가격은 양수여야 해요.")
    .multipleOf(0.01, "가격은 소수점 두 자리까지 허용해요."),
  description: z.string().optional(),
  category: z.enum(["electronics", "food", "clothing"], {
    errorMap: () => ({ message: "유효한 카테고리를 선택해주세요." }),
  }),
});

// 스키마로부터 타입 추론
type CreateProductPayload = z.infer<typeof createProductSchema>;

export async function POST(request: Request) {
  const validation = await validateRequest<CreateProductPayload>(
    request,
    createProductSchema,
  );

  if (!validation.success) {
    return validation.errorResponse; // 유효성 검사 실패 시 에러 응답 반환
  }

  const validatedData = validation.data; // 유효성 검사를 통과한 데이터

  console.log("유효한 상품 데이터:", validatedData);

  // 실제 데이터베이스 저장 로직 등...
  // const newProduct = await db.product.create({ data: validatedData });

  return NextResponse.json(
    {
      message: "상품이 성공적으로 생성되었어요.",
      product: validatedData,
    },
    { status: 201 },
  );
}
```

이렇게 `validateRequest` 함수를 사용하면 Route Handler의 코드가 훨씬 간결해지고, 유효성 검사 로직을 재사용하고 중앙에서 관리할 수 있게 돼요.<br />
에러 응답 형식도 일관되게 유지할 수 있어 API의 신뢰도를 높일 수 있답니다.

## 🧪 실제 코드 예시

### 0️⃣ POST 요청 API 유효성 검사

실제 Next.js 프로젝트에 적용하는 과정을 보여드릴게요.<br />
`app/api/comments/route.ts` 파일을 만들고, 댓글 생성 API를 구현해 봅시다.<br />

```tsx showLineNumbers
// app/api/comments/route.ts
import { NextResponse } from "next/server";
import { z } from "zod";

// 댓글 생성 요청에 대한 스키마 정의
const createCommentSchema = z.object({
  postId: z.string().uuid("유효한 게시글 ID여야 해요."),
  author: z
    .string()
    .min(2, "작성자 이름은 2글자 이상이어야 해요.")
    .max(30, "작성자 이름은 30글자를 넘을 수 없어요."),
  content: z
    .string()
    .min(5, "댓글 내용은 5글자 이상이어야 해요.")
    .max(500, "댓글 내용은 500글자를 넘을 수 없어요."),
});

// 스키마로부터 타입 추론
type CreateCommentPayload = z.infer<typeof createCommentSchema>;

export async function POST(request: Request) {
  try {
    const body: unknown = await request.json(); // unknown으로 먼저 받고 Zod로 검증해요.

    // Zod 스키마로 요청 본문 유효성 검사 및 타입 변환
    const validatedCommentData = createCommentSchema.parse(body); // 유효성 검사 실패 시 에러 발생

    // 유효성 검사를 통과한 데이터는 CreateCommentPayload 타입으로 안전하게 사용 가능해요.
    console.log("새로운 댓글 데이터:", validatedCommentData);

    // 실제 데이터베이스 저장 로직을 여기에 구현해요.
    // 예시: await db.comment.create({ data: validatedCommentData });

    return NextResponse.json(
      {
        message: "댓글이 성공적으로 작성되었어요.",
        comment: validatedCommentData,
      },
      { status: 201 },
    );
  } catch (error) {
    if (error instanceof z.ZodError) {
      // Zod 유효성 검사 에러 처리
      console.error("댓글 유효성 검사 실패:", error.errors);
      return NextResponse.json(
        {
          message: "댓글 작성 요청 데이터가 유효하지 않아요.",
          errors: error.errors.map((err) => ({
            field: err.path.join("."),
            message: err.message,
          })),
        },
        { status: 400 },
      );
    }
    // 기타 예상치 못한 에러 처리
    console.error("댓글 API 처리 중 서버 에러 발생:", error);
    return NextResponse.json(
      { message: "서버 에러가 발생했어요." },
      { status: 500 },
    );
  }
}
```

### 1️⃣ 에러 처리 및 응답 포맷

Zod는 유효성 검사에 실패했을 때 `ZodError` 인스턴스를 던져요.<br />
이 에러 객체 안에는 `errors` 배열이 포함되어 있어서, 어떤 필드에서 어떤 유효성 검사 오류가 발생했는지 상세 정보를 얻을 수 있어요.<br />
이를 활용해서 클라이언트에게 명확하고 구체적인 에러 메시지를 전달할 수 있답니다.<br />

위 `POST` 예시에서는 `error.errors.map()`을 사용하여 에러 배열을 클라이언트 친화적인 형태로 가공하여 반환하고 있어요.<br />
이런 일관된 에러 응답 포맷은 프론트엔드에서 에러를 처리하고 사용자에게 피드백을 제공하는 데 큰 도움이 돼요.

<Blockquote type="tip">
**Zod의 `.safeParse()` 메서드 활용 팁**<br />
`.parse()`는 유효성 검사 실패 시 에러를 던지지만, `.safeParse()`는 에러를 던지지 않고 `{ success: boolean; data?: T; error?: ZodError }` 형태의 결과 객체를 반환해요.<br />
조건문으로 성공 여부를 확인하기 때문에 `try-catch` 블록 없이 더 깔끔하게 코드를 작성할 수 있는 경우가 많아요. 위 `lib/validation.ts` 예시에서 `validate` 함수가 `.safeParse()`를 활용하고 있어요.
</Blockquote>

## ✨ 고급 활용 팁

### 0️⃣ Partial 스키마와 Default 값

- **Partial 스키마**: 기존 스키마를 재사용하면서 일부 필드를 선택적으로 만들고 싶을 때 `schema.partial()`을 사용할 수 있어요. 예를 들어, 사용자 정보 업데이트 API에서는 모든 필드가 필수가 아닐 수 있겠죠.<br />
- **Default 값**: Zod의 `default()` 메서드를 사용하면 필드 값이 제공되지 않았을 때 기본값을 설정할 수 있어요. 이는 API의 유연성을 높여줘요.<br />

```ts showLineNumbers {12-16, 21-22}
import { z } from "zod";

const userProfileSchema = z.object({
  username: z.string().min(3),
  bio: z.string().max(200).optional(),
  profilePictureUrl: z.string().url("유효한 URL 형식이어야 해요.").optional(),
  status: z.enum(["active", "inactive", "pending"]).default("active"),
  updatedAt: z.date().default(() => new Date()),
});

type UserProfile = z.infer<typeof userProfileSchema>;

// 사용자 프로필 업데이트를 위한 Partial 스키마
// 모든 필드가 optional이 돼요.
const updateUserProfileSchema = userProfileSchema.partial();

type UpdateUserProfilePayload = z.infer<typeof updateUserProfileSchema>;

const validUpdate: UpdateUserProfilePayload = {
  bio: "새로운 자기소개입니다.",
  status: "inactive",
}; // username, profilePictureUrl 등은 없어도 유효해요.

console.log(updateUserProfileSchema.parse(validUpdate));
// 결과: { bio: '새로운 자기소개입니다.', status: 'inactive', updatedAt: [현재 날짜] }
// default 값인 updatedAt이 자동으로 추가돼요.
```

### 1️⃣ Union 및 ZodPipe 활용

- **Union**: 여러 스키마 중 하나에 일치하는 데이터를 처리할 때 `z.union([schemaA, schemaB])`를 사용할 수 있어요. 예를 들어, 결제 수단이 신용카드 또는 페이팔 중 하나일 때 유용해요.<br />
- **ZodPipe (커스텀 변환/검증)**: Zod는 `.pipe()` 메서드를 통해 커스텀 변환(transform)이나 추가적인 비동기 유효성 검사 로직을 체이닝할 수 있는 강력한 기능을 제공해요. 예를 들어, 특정 문자열을 파싱하거나, 데이터베이스에서 중복 여부를 확인하는 등의 작업에 활용할 수 있어요.<br />

```ts showLineNumbers {5-13, 17-27}
import { z } from "zod";

// 결제 수단 스키마 (Union 예시)
const creditCardSchema = z.object({
  type: z.literal("creditCard"),
  cardNumber: z.string().regex(/^[0-9]{16}$/, "유효한 신용카드 번호여야 해요."),
  expiryDate: z
    .string()
    .regex(/^(0[1-9]|1[0-2])\/([0-9]{2})$/, "유효한 만료일(MM/YY)이어야 해요."),
});

const paypalSchema = z.object({
  type: z.literal("paypal"),
  paypalEmail: z.string().email("유효한 PayPal 이메일 주소여야 해요."),
});

const paymentMethodSchema = z.union([creditCardSchema, paypalSchema]);

type PaymentMethod = z.infer<typeof paymentMethodSchema>;

// ZodPipe를 활용한 커스텀 검증/변환 (예: 비밀번호 강도 검사)
const strongPasswordSchema = z
  .string()
  .min(8, "비밀번호는 최소 8자 이상이어야 해요.")
  .refine(
    (password) => /[A-Z]/.test(password),
    "비밀번호에 대문자가 포함되어야 해요.",
  )
  .refine(
    (password) => /[a-z]/.test(password),
    "비밀번호에 소문자가 포함되어야 해요.",
  )
  .refine(
    (password) => /[0-9]/.test(password),
    "비밀번호에 숫자가 포함되어야 해요.",
  )
  .refine(
    (password) => /[^A-Za-z0-9]/.test(password),
    "비밀번호에 특수문자가 포함되어야 해요.",
  );

console.log(
  paymentMethodSchema.parse({
    type: "creditCard",
    cardNumber: "1234567890123456",
    expiryDate: "12/25",
  }),
);

try {
  strongPasswordSchema.parse("password"); // 에러 발생
} catch (error) {
  if (error instanceof z.ZodError) {
    console.error(
      "약한 비밀번호:",
      error.errors.map((err) => err.message),
    );
  }
}
```

`refine()` 메서드는 ZodPipe의 한 종류로, 사용자 정의 유효성 검사 로직을 추가할 때 유용해요.<br />
이를 통해 Zod가 기본적으로 제공하지 않는 복잡한 비즈니스 로직 기반의 유효성 검사도 쉽게 구현할 수 있답니다.

## 📝 정리

### 0️⃣ 핵심 요약

Next.js App Router에서 Zod와 TypeScript를 함께 사용하는 것은 API 개발의 효율성과 안정성을 크게 향상시키는 강력한 조합이에요.<br />

- **Zod**는 런타임 데이터 유효성 검사와 TypeScript 타입 추론을 동시에 제공하여 **단일 진실 공급원(Single Source of Truth)** 역할을 해요.<br />
- **Route Handler**에 Zod 스키마를 적용하면 클라이언트로부터 들어오는 요청 데이터를 **안전하게 검증**하고, 동시에 **타입 안전성을 확보**할 수 있어요.<br />
- 커스텀 유효성 검사 유틸리티나 미들웨어 패턴을 만들면 **코드 중복을 줄이고** API의 **일관된 에러 처리**를 구현할 수 있답니다.<br />
- `partial()`, `default()`, `union()`, `refine()` 등 Zod의 **다양한 기능을 활용**하여 복잡한 유효성 검사 요구사항도 유연하게 처리할 수 있어요.<br />
