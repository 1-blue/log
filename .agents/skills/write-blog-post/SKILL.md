# 블로그 MDX 작성

## 준비

- 저장소 루트의 `AGENTS.md`를 따른다.
- 새 파일을 만들거나 경로·frontmatter를 바꿀 때 `references/frontmatter-and-paths.md`를 전부 읽는다.
- 본문을 작성하거나 크게 고칠 때 `references/writing-and-mdx.md`를 전부 읽는다.
- 대상 카테고리에서 성격이 비슷한 최근 글 1~2개를 확인해 어조와 깊이를 맞추되 문장을 복사하지 않는다.
- 요청이 작성, 수정, 검수 중 무엇인지 구분한다. 카테고리나 AI 분류가 결과를 크게 바꾸는데 사용자 의도와 주변 파일로 결정할 수 없을 때만 질문한다.

## 작업 흐름

1. 대상 파일과 공개 경로를 정한다.
   - 기존 글을 수정할 때는 요청이 없는 한 경로와 `createdAt`을 유지한다.
   - 새 글은 같은 카테고리의 파일명 관례를 따른다.
   - 사용자가 AI 컬렉션을 요청한 경우에만 `ai/`, `ai: true`, AI 표시를 사용한다. Codex가 도왔다는 이유만으로 일반 글을 AI 컬렉션으로 옮기지 않는다.
2. 근거를 준비한다.
   - 개인 경험과 일반 기술 사실을 구분한다.
   - 버전, API, 보안, 성능처럼 달라질 수 있는 주장은 공식 문서나 1차 자료로 확인한다.
   - 경험, 테스트 결과, 경력, 사용한 모델을 지어내지 않는다.
3. frontmatter를 작성한다.
   - 새 글은 모든 기본 필드를 포함하고 한국 시간 `YYYY-MM-DD HH:mm:ss`를 사용한다.
   - 기존 글의 의미 있는 본문을 수정하면 `sitemap.lastmod`만 현재 한국 시간으로 갱신한다. 공개일을 바꾸라는 요청이 없으면 `publishedAt`은 유지한다.
   - 완성된 새 글은 기존 기본값인 `draft: false`를 사용한다. 미완성 내용이나 TODO가 남으면 `draft: true`로 둔다.
4. 본문을 작성한다.
   - frontmatter 제목을 본문 `#` 제목으로 반복하지 말고 본문은 `##`부터 시작한다.
   - 문제와 맥락, 핵심 설명, 필요한 예시, 정리 순서를 주제에 맞게 구성한다. 모든 글에 같은 섹션명을 강제하지 않는다.
   - 짧은 한국어 문단과 구체적인 설명을 사용한다.
5. MDX와 자산을 연결한다.
   - 전역 등록된 컴포넌트만 import 없이 사용한다.
   - 이미지는 게시글 경로와 대응하는 public 디렉터리에 놓고 루트 기준 URL로 참조한다.
   - 실제 코드와 명령은 언어가 지정된 fenced code block으로 작성한다.
6. 스스로 검수한다.
   - 제목, 설명, 태그와 본문의 약속이 일치하는지 확인한다.
   - 링크, 이미지 경로, JSX 태그, 코드 예시, 사실 주장, AI 고지가 정확한지 확인한다.
   - 비밀값, 개인정보, 근거 없는 절대 표현과 가짜 인용을 제거한다.
7. 검증한다.
   - 변경한 MDX에 `pnpm exec prettier --write <파일>`을 실행한다.
   - `pnpm --filter blog typecheck`를 실행한다.
   - 새 파일, 파일 이동, frontmatter 구조 또는 MDX JSX를 바꾼 경우 `NEXT_PUBLIC_CLIENT_URL=http://localhost:3000 pnpm --filter blog build`도 실행한다.
   - 실패한 검증을 숨기지 말고 원인과 영향 범위를 보고한다.

## 완료 보고

- 생성 또는 수정한 파일, 예상 공개 URL, `draft`와 AI 분류 상태를 요약한다.
- 실행한 검증과 결과를 적는다.
- 남은 사실 확인 항목, 미완성 부분, 배포 전 주의점이 있으면 명시한다.
