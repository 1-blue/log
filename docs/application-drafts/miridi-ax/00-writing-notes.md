## 1. 보여줄 인물상

> 반복되는 불편을 발견하면, 필요한 기술을 배워 직접 개선하는 개발자.

“기준을 문서와 코드로 남긴다”는 표현은 무엇을 했는지 바로 떠올리기 어렵다는 의견을 반영해 자기소개에서 뺐습니다. 문서화는 대표 성향이 아니라, 특정 문제를 개선한 방법으로 설명합니다.

| 자기소개를 뒷받침할 행동            | 연결할 사례                                       |
| ----------------------------------- | ------------------------------------------------- |
| 직접 사용하며 불편을 찾음           | 공고 본문 누락, n8n과 관리자 상태 불일치 발견     |
| 필요한 기술을 배워 적용함           | story-dict의 Docker·AWS 배포와 OpenAPI 타입 생성  |
| 같은 문제를 반복하지 않도록 바꿈    | 본문 파서 회귀 테스트, jabaek의 정책·테스트 연결  |
| 기존 사용 환경과 변경 비용을 고려함 | 오픈놀 레거시의 점진 전환, 실무 OpenAPI 도입 보류 |

### “문서와 코드로 남겼다”는 근거가 있나?

자료는 있습니다. 다만 증명하는 범위를 나눠야 합니다.

1. **story-dict:** 배포·캐시 블로그 글과 배포 Workflow가 있습니다. 왜 캐시를 도입했는지, 어디서 기존 이미지를 재사용하는지 연결할 수 있습니다.
2. **jabaek:** 정책 원본·요구사항 ID·테스트·구현 위치를 연결하는 문서와 CI 설정이 있습니다. “문서화에 관심이 있다”보다 실제 예시 하나를 보여주는 편이 분명합니다.
3. **Career Ops:** 장애별 확인 순서가 있는 Runbook과 진단 API·회귀 테스트가 있습니다. 운영 절차를 마련했다는 근거이지, 다른 사람이 이 문서로 장애를 해결했다는 증거는 아닙니다.

개인 프로젝트에서 타인의 피드백은 받지 않았다는 답변을 반영했습니다. 동료 평가나 사용자 만족도 대신 직접 관찰한 현상과 변경 내용을 사용합니다. 실무 포트폴리오에는 동료 피드백이 적혀 있지만, 이번 초안에서는 다시 확인하지 않은 인용을 넣지 않았습니다.

## 3. 지원 직무와 연결한 부분

목표는 **미리디 AX Engineer - Infra**입니다. 디자이너 지원용 원고가 아닙니다.

원래 전달받은 [Wanted 공고](https://www.wanted.co.kr/wd/384409)는 이번 조회에서 403이 반환됐습니다. 회사가 등록한 동일 직무명의 [랠릿 공고](https://www.rallit.com/positions/4396/미리디-ax-엔지니어-infra-ax-engineer-infra)로 업무 방향을 보완 확인했습니다. 두 페이지가 모든 문장까지 동일하다고 보장하지 않으며, 지원 직전에는 실제 지원 페이지를 다시 확인해야 합니다.

공고에서 확인한 방향은 기존 운영 절차를 배우고, 로그로 오류를 확인하며, 반복 업무와 배포·알림·문서를 개선하는 것입니다. 이를 기준으로 다음처럼 배치했습니다.

- Cloudflare·n8n·LLM API: Career Ops의 구체적인 역할 분담과 실패 처리.
- 작은 서비스 배포·자동화: story-dict의 Docker·AWS·GitHub Actions.
- AI 도구 결과 검증: jabaek의 정책과 테스트 연결, Career Ops의 인용문 검사.
- 협업·변경 범위 판단: 오픈놀 경력. 프론트엔드라는 이유로 삭제하지 않음.

Terraform·Datadog·Langfuse나 Cloudflare 제품 전반을 다뤘다는 표현은 넣지 않았습니다. AWS 경험은 인접 경험으로 제시하되 Cloudflare 운영 숙련을 대신한다고 쓰지 않습니다.
