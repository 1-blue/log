## 2. 취업 준비 서비스 — 공고와 개인 자료를 비교하는 작업 연결

2026.09 - 진행 중 · 개인 프로젝트 · Codex와 함께 구현

### 만들게 된 이유

공고를 읽고 이력서·포트폴리오의 어떤 경험이 맞는지 확인한 뒤, 면접에서 설명할 내용을 따로 정리해야 했습니다. 공고 원문과 사용할 문서, 분석 결과를 한곳에서 확인하고 싶었습니다.

기존 블로그에 관리자 화면을 추가해 공고 수집, 문서 버전 관리, AI 비교 결과와 면접 답변 작성을 연결했습니다.

### 도구별 역할

| 도구               | 이 프로젝트에서 맡긴 역할                                  |
| ------------------ | ---------------------------------------------------------- |
| Next.js            | 공고·문서 관리, 실행 상태와 분석 결과 확인                 |
| Cloudflare Workers | 관리자 인증, 요청·결과 검증, 실행 상태와 데이터 저장       |
| n8n                | 외부 공고 수집, PDF 처리, AI 요청, 결과 callback 순서 구성 |
| Supabase           | 문서 파일·공고 스냅샷·분석 결과·사용자 작성 내용 보관      |

AI 결과를 받는 것만으로 분석이 끝났다고 보지 않고, Worker에서 형식과 근거를 확인한 뒤 저장하도록 했습니다. 사용한 문서 버전과 공고 스냅샷을 기록해 결과를 볼 때 어떤 자료를 비교했는지 확인할 수 있게 했습니다.

### 직접 사용하며 바꾼 부분

공고의 주요 업무만 들어오거나 근무지역에 불필요한 안내 문구가 섞이는 현상을 발견했습니다. 또 분석 근거가 짧은 단어로만 보여 어떤 경험을 말하는지 이해하기 어려웠습니다.

발견한 사례를 바탕으로 본문 정규화와 섹션 분류를 보완하고, 원문 인용을 확인하는 코드와 테스트를 추가했습니다. 화면은 지원 정보·채용공고·분석 탭으로 나누고 긴 내용은 접어서 필요한 부분부터 볼 수 있게 했습니다.

### 현재 확인 범위

로컬에서 실제 분석 성공을 확인한 뒤 후속 개선을 진행했습니다. 2026년 9월 20일 오프라인 검증 기록에는 테스트·빌드·격리 DB 검사가 통과한 것으로 남아 있습니다. 다른 공고의 수집 품질과 반복 사용 안정성, 최신 자동 배포의 운영 결과는 별도로 확인해야 합니다.

> 증빙 배치: 지원 상세의 탭 화면 1장과 공고 섹션 화면 1장. 긴 워크플로우 전체를 축소해 넣기보다 위 역할 표 옆에 주요 흐름만 표시합니다.

## 3. 취업 준비 서비스 — 실행 성공과 분석 결과 저장을 구분하기

### 관찰한 문제

n8n 실행 목록에서는 성공으로 표시됐지만 관리자 화면에는 분석 실패가 나타났습니다. 다른 실행에서는 callback 전송이 실패한 뒤에도 관리자 화면이 분석 중으로 남았습니다.

처음에는 어디를 확인해야 하는지 몰라 n8n 실행 화면과 브라우저 응답을 함께 보며 AI에 원인 분석을 요청했습니다. 이 과정에서 워크플로우 정상 종료와 유효한 분석 결과 저장이 서로 다른 상태라는 점을 확인했습니다.

### 바꾼 확인 순서

```text
작업 접수 → AI 응답 → callback 응답 → 결과 검증·DB 저장 → 관리자 결과 조회
```

화면의 문구만으로 원인을 추측하지 않고, 같은 작업이 어디까지 진행됐는지 확인할 수 있도록 진단 응답을 보완했습니다. 단계별 이벤트, 안전한 오류 코드, 시도 횟수와 Request ID를 제공합니다.

### 코드에 반영한 내용

- 결과의 형식·근거 검증에 실패하면 저장 단계의 실패를 기록하도록 했습니다.
- 종료 callback이 오지 않는 경우를 위해 마지막 heartbeat가 오래된 작업을 확인하고 복구하는 경로를 두었습니다.
- 완료·취소된 작업에 늦게 도착한 결과가 현재 상태를 덮어쓰지 않도록 종료 상태를 확인합니다.
- 로그는 실행을 구분하는 필드 위주로 구성하고, 원문과 토큰을 무분별하게 기록하지 않도록 했습니다.

### 결과와 남은 확인

현재 코드에서는 “계속 분석 중”이라는 표시 뒤에 있는 작업 이벤트와 저장 여부를 확인할 수 있습니다. 원인이 아직 확인되지 않은 상태와 결과 검증이 실패한 상태를 구분할 근거를 마련했습니다.

문제 발견과 동작 확인은 직접 진행했고, 원인 분석과 코드 수정·테스트 작성은 AI와 함께 진행했습니다. 다음 확인 과제는 실행 한 건의 로그와 DB 상태를 직접 연결해 이 진단 정보가 실제로 도움이 되는지 검증하는 것입니다.

> 증빙 배치: 동일 실행의 관리자 상태·n8n callback 응답·저장 결과. 과거 실행 자료가 없다면 현재 진단 화면을 “개선 후 화면”으로만 사용하고, 과거 로그를 재현한 것처럼 만들지 않습니다.

## 4. story-dict — 배포 과정을 직접 구성하고 반복 빌드 줄이기

2024.10 - 2025.01 · 이후 배포·캐시 개선 · 개인 프로젝트

단어나 표현을 질문하는 웹 서비스입니다. 기술 검증과 학습 목표를 진행한 후 인프라 유지 비용을 고려해 운영을 종료했습니다.

### 배포를 익힌 방식

프론트엔드 코드가 실행되는 곳뿐 아니라 API와 DB, 이미지 저장소가 어떻게 연결되는지 이해하고 싶었습니다. Next.js와 NestJS를 각각 Docker 이미지로 만들고 EC2에서 실행했으며, ECR·RDS·S3를 연결했습니다.

기존 아키텍처 자료에는 RDS를 Private Subnet에 두고, 보안 그룹으로 접근 범위를 제한한 구성이 남아 있습니다. Route 53·ACM·로드밸런서로 도메인과 HTTPS 요청 흐름을 구성했습니다.

### 같은 소스를 다시 빌드하던 문제

코드가 바뀌지 않아도 CI와 배포 과정에서 같은 빌드를 다시 실행하는 경우가 있었습니다. 변경 파일을 확인하는 것만으로는 서로 다른 실행에서 생기는 중복 작업을 줄이기 어려웠습니다.

Turborepo와 S3에 빌드 결과를 보관하고, 같은 소스 해시에 해당하는 ECR 이미지가 있으면 다시 빌드하지 않고 사용하도록 구성했습니다. GitHub Actions에서 배포를 실행하고 결과 알림을 확인하는 흐름도 연결했습니다.

### 남긴 결과

프론트엔드·백엔드 이미지의 생성, 저장, 배포 과정을 직접 구성했고, 기존 결과를 재사용하는 경로를 만들었습니다. 선택 이유와 설정은 블로그의 배포·캐시 글에 정리했습니다.

개선 후 시간을 동일 조건에서 비교한 기록이 부족해 절감률은 기재하지 않았습니다. 캐시가 있는 경우와 없는 경우의 동작 차이를 설명하는 것이 현재 자료로 보여줄 수 있는 결과입니다.

> 증빙 배치: 기존 포트폴리오의 AWS 구조도와 GitHub Actions의 이미지 재사용 분기. 현재 서비스가 종료된 상태임을 그림 캡션에도 표시합니다. 과거 배포 스크립트를 현재 운영의 권장 절차로 그대로 소개하지 않습니다.

## 5. story-dict — API 문서와 타입을 따로 옮겨 적지 않도록

### 실무에서 발견한 불편

API 문서에는 문자열로 적혀 있는데 실제 응답에는 `null`이 포함되는 등, 문서와 응답을 다시 확인해야 하는 일이 있었습니다. 응답 타입을 프론트엔드에 수동으로 작성하면 같은 변경을 여러 곳에 반영해야 했습니다.

### 개인 프로젝트에서 검증한 방법

기존 REST API 구조에서 적용할 수 있는 방식을 찾았습니다. NestJS의 DTO·Controller 정보를 바탕으로 OpenAPI 명세를 만들고, `openapi-typescript`로 프론트엔드 타입을 생성해 요청 계층에 연결했습니다.

타입을 별도로 복사하는 작업을 줄이고, 명세를 갱신한 뒤 타입 검사로 영향받는 코드를 확인할 수 있게 했습니다. 다만 생성 타입이 실제 모든 서버 응답의 정확성까지 보장하는 것은 아니므로 런타임 검증과는 구분했습니다.

### 실무 제안과 적용 범위

개인 프로젝트에서 확인한 방식과 적용 조건을 팀에 제안했습니다. 당시에는 우선 개발해야 할 기능과 백엔드 작업 부담 때문에 도입이 보류됐습니다.

적용은 개인 프로젝트에 한정됐습니다. 팀에 제안하면서 도구의 장점뿐 아니라 백엔드 작업량과 기존 구조의 변경 비용도 함께 설명해야 한다는 점을 배웠습니다.

> 증빙 배치: 실제 DTO·생성 타입·이를 사용하는 API 호출 코드의 짧은 예시. 문서와 구현이 어긋났던 회사 내부 자료는 공개하지 않습니다.

## 6. jabaek — AI와 작업할 때 바뀌면 안 되는 규칙 정리

2026.07 - 진행 중 · 개인 프로젝트 · AI와 기획·구현

다섯 명의 AI 용의자와 대화하며 사건을 해결하는 웹·모바일 추리 게임입니다. Next.js·Expo WebView·Supabase를 사용했습니다.

### 빨리 만들면서 생긴 문제

AI와 반복해서 작업하면 문서가 새로 생기거나, 같은 정책을 서로 다르게 설명하는 일이 있었습니다. 사건 생성과 플레이, 결제처럼 여러 부분에 걸친 규칙은 어떤 문서를 기준으로 수정해야 하는지 다시 확인해야 했습니다.

### 바꾼 작업 방식

영역별로 정책 원본을 정하고, 정책의 값과 의미를 설명하는 문서를 연결했습니다. 요구사항 ID를 통해 정책과 테스트, 구현 위치를 찾아갈 수 있게 했으며, 작업 순서는 정책 확인과 실패 테스트부터 시작하도록 정했습니다.

현재 저장소에는 이 연결과 문서 불일치를 확인하는 검사 명령이 있고, CI에서 공통 검증 명령을 실행하도록 구성돼 있습니다. 외부 AI 응답의 형식 검증과 서비스의 상태·정답 판정도 분리했습니다.

### 결과와 한계

AI가 이전 작업과 다른 규칙을 만들었는지 확인할 기준을 마련했습니다. 모든 오류를 예방했다는 의미는 아니며, 규칙을 추가할 때 문서와 테스트도 함께 유지해야 하는 비용이 생겼습니다.

결제와 플레이 상태처럼 오류의 영향이 큰 정책은 엄격하게 추적하고, 단순한 UI 세부 동작은 코드와 테스트에 맡겼습니다. 모든 변경에 같은 수준의 문서를 요구하지 않도록 범위를 나눴습니다.

> 증빙 배치: 정책 하나 → 요구사항 ID → 연결 테스트 → 구현 위치. 전체 문서 트리를 보여주는 대신 본인이 설명할 수 있는 규칙 하나를 고릅니다. 저장소는 비공개이므로 공개 가능한 부분만 제출 자료에 옮깁니다.

## 7. 오픈놀 — 기존 서비스를 바꿀 때 먼저 정한 범위

2023.09 - 2025.09 · Frontend Developer

### 한 번에 바꾸기 어려웠던 관리자 화면

관리자 화면의 요청 처리가 여러 파일에 나뉘어 있었고, 기존 요구사항 이력과 테스트가 충분하지 않았습니다. 전체를 바꾸면 구조는 일관되게 만들 수 있지만, 정상 동작을 확인할 범위가 너무 커졌습니다.

신규 기능이나 수정할 화면이 생길 때 기존 동작과 연결된 사용자 화면을 확인하고, 그 범위부터 서버 상태 관리를 SWR로 옮겼습니다. 기획자와 영향 범위를 확인하며 기능 변경과 구조 개선을 함께 진행했습니다.

### 공통 UI를 적용한 경험

B2B·B2C·관리자 화면에 사용할 버튼·툴팁·드롭다운 등 공통 컴포넌트의 구현과 Storybook 문서화에 참여했습니다. 기존 사용처와 예외를 확인하고 디자이너와 조율하며 적용했습니다.

공용 컴포넌트가 있어도 디자인과 개발의 속성명, 커스텀 허용 범위가 달라 다시 협의하는 일이 남았습니다. 다음에는 외형뿐 아니라 지원할 속성과 예외를 초기에 함께 정하고 싶습니다.

### AX 업무에 가져가려는 경험

새 구조가 더 편리해 보여도 기존 사용 흐름과 확인할 수 있는 범위를 먼저 살폈습니다. 내부 도구를 개선할 때도 사용하는 사람과 기대 동작을 확인하고, 바꾼 뒤 영향을 함께 살피는 방식으로 접근하고 싶습니다.

## 편집 메모 — 제출 전 제외

### 강조할 것

- 도구의 개수보다 직접 발견한 문제와 변경한 동작을 먼저 보여줍니다.
- Career Ops는 직무와 가까운 현재 사례, story-dict는 인프라·배포 학습의 기반, jabaek은 AI 협업과 규칙 관리의 사례로 역할을 나눕니다.
- 실무 경력은 협업과 변경 범위 판단을 증명합니다. 상세 React 구현은 기존 프론트엔드 포트폴리오 링크로 넘깁니다.
- 개인 프로젝트에는 타인의 피드백을 넣지 않습니다. 사용자 본인이 확인한 현상과 저장소에서 확인되는 변경을 씁니다.

### 보완 후 넣을 자료

1. 동일 분석 실행의 Request ID와 실패 단계, 수정 후 확인 결과를 개인정보 없이 한 장에 정리합니다.
2. story-dict 개발 기간을 본개발과 2025년 후속 개선으로 나눠 확정합니다.
3. jabaek의 출시 시점·스토어 링크를 확인하면 “출시”를 추가합니다. 설치 수·매출은 확인된 값만 사용합니다.
4. 최신 자동 배포의 성공 기록이 확보되면 Career Ops의 별도 성과로 추가합니다. 지금은 구현과 운영 검증을 구분합니다.
5. 문서를 보고 다른 사람이 재현했다는 피드백은 아직 없으므로, 운영 인수인계 성과로 표현하지 않습니다.
