## 🚀 취업 준비 과정을 직접 만들어보기

채용공고를 보고 이력서와 포트폴리오를 맞춰보는 일을 조금 덜 번거롭게 만들고 싶었어요. 어떤 경험이 공고의 요구사항과 연결되는지 확인하고, 부족한 부분은 면접 전에 준비할 수 있으면 좋겠다고 생각했어요.

그래서 기존 블로그에 개인용 취업 준비 관리 화면을 붙였어요. 공고를 등록하고, 올려둔 PDF를 선택하고, AI 분석 결과와 예상 면접 질문을 확인하는 서비스예요.

처음에는 공고 본문과 PDF를 AI에 전달하면 핵심 기능은 끝날 것 같았어요. 그런데 직접 화면에서 사용해보니 분석 요청보다 그 전후에 확인할 일이 많았어요. 공고 본문이 일부만 수집되기도 했고, n8n에는 성공으로 나오는데 관리자 화면에서는 실패로 보이기도 했어요.

이번 글에서는 기능 전체를 소개하기보다, 이 과정에서 무엇을 성공으로 봐야 하는지 다시 정했던 이야기를 적어보려고 해요.

코드와 테스트는 Codex와 함께 작성했어요. 저는 관리자 화면에서 직접 시도하고, 기대와 다른 결과를 캡처해 전달하고, 어떤 동작으로 바꿀지 정했어요. 이 글은 그 과정에서 함께 원인을 확인하고 수정한 기록이에요.

## 🧩 Worker와 n8n은 각각 무슨 일을 하나요?

관리자 화면에서 누른 버튼이 바로 OpenAI를 호출하는 구조는 아니에요. 요청은 Cloudflare Worker를 거치고, n8n이 외부 서비스와 통신한 결과를 다시 Worker로 보내요.

```text
관리자 화면 → Worker: 권한 확인, 실행 등록
Worker → n8n: 수집·분석 작업 요청
n8n → Wanted / OpenAI: 본문 수집, AI 요청
n8n → Worker: 처리 결과 전달
Worker: 결과 검증 → Supabase: 저장
관리자 화면 → Worker: 저장된 상태와 결과 조회
```

Worker에는 관리자 권한 확인, 요청 형식 검증, 작업 상태와 결과 저장을 두었어요. n8n에는 공고 수집, PDF 처리, AI 요청과 결과 전달 순서를 구성했어요. 외부 호출이 성공했더라도 저장할 수 있는 결과인지는 Worker에서 다시 확인해요.

이렇게 나누면 n8n에서 어느 단계까지 실행됐는지 볼 수 있고, 데이터에 적용할 규칙은 API 쪽에서 관리할 수 있어요. 대신 중간 연결이 늘어나기 때문에, 어느 구간의 성공을 보고 있는지 구분해야 했어요.

## 🤔 n8n에는 성공인데 왜 화면에는 실패일까요?

실제로 분석을 요청했을 때 관리자 화면에 `OpenAI 요청을 처리할 수 없습니다`라는 문구가 나왔어요. n8n 실행 목록에는 `Succeeded`가 보여서 처음에는 분기가 잘못된 건지, 화면이 이전 상태를 보여주는 건지 알기 어려웠어요.

여기서 놓친 점은 워크플로우가 오류를 처리하는 경로로 끝나도 실행 자체는 정상 종료될 수 있다는 점이었어요. 성공한 AI 결과를 저장한 경우와, AI 오류를 받아 실패 상태를 전달한 경우를 같은 실행 목록만 보고 구분하려 했던 거예요.

반대로 결과를 전달하는 callback이 실패하면 n8n에서는 실패가 보이는데 관리자 화면은 계속 분석 중으로 남을 수도 있었어요. 종료 정보가 Worker에 도착하지 않았는지, 도착했지만 처리되지 않았는지는 callback 응답과 저장 상태를 함께 봐야 해요.

이 증상들이 모두 같은 원인으로 발생한 것은 아니에요. 다만 실행 목록의 색상이나 HTTP 응답 코드 하나만 보고 전체 분석이 성공했다고 판단하면 안 된다는 점은 같았어요.

확인할 순서를 다음처럼 나눴어요.

1. n8n이 작업 요청을 받았는지 확인해요.
2. AI 호출이 결과를 반환했는지, 오류를 반환했는지 확인해요.
3. n8n이 Worker에 보낸 callback의 응답을 확인해요.
4. Worker가 결과를 검증하고 DB에 저장했는지 확인해요.
5. 관리자 화면에서 같은 작업의 저장 결과를 확인해요.

상태를 조회한 요청이 `200`이라고 해서 분석도 성공한 건 아니었어요. 조회 API는 정상적으로 응답하면서 본문에는 `failed` 상태를 담을 수 있어요. 이걸 구분하고 나니 개발자 도구에서 무엇을 봐야 하는지도 조금 명확해졌어요.

## 🔎 실패한 위치를 화면에서도 확인할 수 있게

매번 n8n과 개발자 도구를 오가는 건 불편했어요. 그래서 분석 진단 응답에 작업 이벤트, 처리 단계, 오류 코드, 시도 횟수와 Request ID를 담고, 관리자 화면에서도 확인할 수 있게 했어요.

예를 들어 AI 응답을 받았지만 결과 검증을 통과하지 못한 경우에는 저장 단계의 실패로 기록해요. 현재 Worker에는 이 경우 작업을 실패 상태로 전환하는 처리가 있어요. 검증 실패를 응답으로 돌려주기만 하고 작업 상태는 계속 실행 중으로 두지 않도록 한 거예요.

아예 callback이 도착하지 않은 상황은 다르게 처리해야 했어요. 응답이 없다는 사실만으로 인증 문제인지, 네트워크 문제인지, n8n이 중단됐는지까지 알 수는 없으니까요. 현재는 마지막 heartbeat를 기준으로 오래 멈춘 작업을 확인하고 복구할 수 있게 했어요.

로그에도 모든 데이터를 담지는 않았어요. Request ID, 처리 시간, 상태 코드처럼 실행을 구분할 값은 남기고, 이력서 원문이나 토큰처럼 문제 확인에 불필요한 값은 로그 필드에서 제외하는 구조를 두었어요.

이전에는 실패 문구만 보고 어디를 봐야 할지 물어봤어요. 이제는 작업 ID를 기준으로 단계와 저장 상태를 확인할 수 있고, 응답이 끊긴 경우의 확인 순서도 운영 문서에 남아 있어요. 이 흐름을 운영 로그에서 직접 따라가 보는 일은 다음 확인 과제로 두었어요.

## 📄 AI에 보내기 전에 공고 본문부터 확인하기

분석 요청이 끝나더라도 입력이 잘못되면 결과를 믿기 어려워요. 공고 수집 화면을 확인하면서 이 문제도 발견했어요.

주요 업무만 가져오고 다른 항목이 빠지는 경우가 있었고, 근무지역 아래에 안내 문구와 추천 공고 관련 내용이 붙기도 했어요. `&#x20;` 같은 문자가 그대로 보이거나 문장이 중간에서 잘린 것처럼 표시되는 경우도 있었어요.

문자 하나를 지우는 것보다 먼저, 어디에서 내용이 달라졌는지 나눠봐야 했어요. 받은 HTML, 추출된 본문, 섹션별 분류, AI에 보내는 입력, 화면 표시가 서로 다른 단계였기 때문이에요.

현재 파서는 주요 업무와 자격요건 같은 섹션을 나누고, 공고와 관계없는 문구를 제외하는 규칙을 갖고 있어요. 여기에 숫자형 HTML entity를 해석하고, 보이지 않는 문자와 불필요한 제어문자를 정리하는 처리를 보완했어요.

여기서 `+`를 전부 없애면 `C++`처럼 필요한 표현까지 바뀔 수 있어요. 또 문장 안에 `자격 요건`이라는 단어가 나왔다고 그 위치에서 무조건 섹션을 나누면 본문이 잘릴 수 있고요. 이런 입력을 테스트에 넣어 정상 표현과 문장을 유지하는지 확인했어요.

이 테스트가 통과했다고 모든 원티드 공고를 완벽하게 읽는다고 볼 수는 없어요. 지금 확인한 사례를 다시 망가뜨리지 않는 검증이고, 실제 다른 공고에서도 본문이 빠지지 않는지는 더 확인해야 해요.

## 📝 분석 결과도 근거와 함께 보기

초기 결과 화면에서는 공고 근거와 개인 자료 근거에 `API`, `자동화`처럼 짧은 단어만 보이는 경우가 있었어요. 단어가 있다는 사실은 확인할 수 있지만, 어떤 경험을 근거로 판단했는지는 읽기 어려웠어요.

그래서 결과를 볼 때 점수만 보는 대신 선택한 문서와 인용문을 함께 확인하도록 방향을 바꿨어요. Worker에서는 분석에 선택한 이력서·포트폴리오 텍스트에 인용문이 있는지 검사해요. 이 검사는 문서에 없는 문장을 근거로 쓰는 문제를 막기 위한 것이에요.

여기에도 한계는 있어요. 인용문이 실제 문서에 있다는 것과 AI의 해석이 맞다는 것은 다른 확인이에요. 문서에 `Docker`가 적혀 있다고 장기간 운영 경험까지 증명되는 건 아니니까요.

그래서 현재 점수는 자료와 공고 요구사항을 비교한 참고값으로 보고 있어요. 실제 지원 판단이나 답변에 사용할 때는 어떤 문장과 경험이 연결됐는지 직접 확인해야 해요.

## 🧪 수정한 뒤 같은 문제를 다시 확인하기

기능을 고칠 때마다 확인할 항목이 늘어나서, 타입 검사와 테스트, 빌드, DB 검사를 `pnpm verify:offline`으로 묶었어요. DB 검증은 평소 사용하는 데이터베이스를 초기화하지 않도록 임시 Supabase에서 실행해요.

2026년 9월 20일 검증 기록에는 계약·Blog·Worker 테스트와 DB pgTAP, production build가 통과한 것으로 남아 있어요. 이 검사는 AI와 Slack을 실제로 호출하는 운영 시험과는 별개예요. 코드의 정해진 동작을 확인하는 데 쓰고, 외부 연결은 따로 확인해야 해요.

로컬에서 실제 분석이 성공한 결과는 한 차례 확인했지만, 이후 바뀐 코드까지 운영 환경에서 전부 확인한 것은 아니에요. 최신 배포 자동화와 로그 저장 설정도 운영 적용 결과를 확인한 뒤에야 사용 경험으로 덧붙일 수 있어요.

## 💭 이번에 달라진 점

처음에는 AI 요청이 가고 결과가 오면 된다고 생각했어요. 직접 사용해보니 입력이 제대로 수집됐는지, 결과가 저장됐는지, 실패했을 때 다시 시도할 수 있는지가 함께 필요했어요.

프론트엔드에서 버튼 뒤에 있는 상태를 받아 보여줄 때도 비슷한 일이 있었는데, 이번에는 그 상태가 여러 서비스를 거쳐 만들어지는 과정까지 보게 됐어요. 화면에서 발견한 불편을 수정하다가 API와 워크플로우, 저장 상태까지 확인 범위가 넓어진 셈이에요.

다음에는 새 기능을 늘리기보다 실제 공고 몇 건으로 본문 누락과 분석 근거를 확인하고 싶어요. 실패한 실행도 하나 골라 Request ID부터 저장 상태까지 직접 따라가 보려고 해요. 확인한 과정을 남기면 지금 만든 진단 화면과 운영 문서가 실제로 도움이 되는지도 알 수 있을 것 같아요.

## 작성 메모 — 게시 전 제외

- 중심 주제는 “AI 취업 서비스 기능 소개”보다 “사용하면서 성공·실패 판단 기준을 고친 과정”입니다.
- 실제 과거 오류의 정확한 HTTP 상태·DB 거부 사유는 보존된 실행 기록을 다시 확보하기 전까지 넣지 않습니다. 여러 차례 발생한 오류를 한 가지 원인으로 합치지 않았습니다.
- `&#x20;`와 문장 경계 보존은 코드·테스트로 확인했습니다. 모든 HTML entity 지원, 모든 잘림 해결, 공고 전체 수집 보장은 주장하지 않습니다.
- 실제 로그를 수록할 때는 원본을 확인한 후 비밀값과 개인정보를 지웁니다. 이 초안에는 가상의 성공 로그를 넣지 않았습니다.
- 추천 이미지: 기존 n8n 실행 화면과 관리자 실패 화면 한 쌍, 수정된 진단 화면, 섹션별 공고 본문 화면. 이미지의 작업 ID·발생 시각이 같은지 확인하고 캡션을 붙입니다.
- `pnpm verify:offline` 통과는 2026-09-20의 기록입니다. 이 글 작성 과정에서 재실행한 결과가 아닙니다.
- 첫 분석 성공은 대화에서 사용자가 확인한 사실입니다. 최신 코드의 운영 전체 흐름 성공이나 반복 안정성으로 확대하지 않습니다.
