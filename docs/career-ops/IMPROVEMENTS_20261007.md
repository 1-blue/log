# Career Ops 개선 작업과 완료 기준

사용자가 확정한 개발 범위이며, 운영 초기화·배포·과거 문서 일괄 재추출은 이번 개발 과정에서 자동 실행하지 않는다.

## 작업 범위

- [x] 문서 업로드 접수 및 OCR 완료·실패 Slack 알림
- [x] Slack 오류 분류와 안전한 오류 기록
- [x] 루트 알림 실패 후 스레드 복구, 재시도와 중복 방지
- [x] 모든 AI 호출의 사용량·비용 기록 (시작, 성공, 실패, 재시도, 미집계 포함)
- [x] 관리자 사용량·비용 대시보드 (일별 그래프, 작업별 표)
- [x] 관리자 수동 잔액 기준 등록과 추정 잔액 표시
- [x] PDF 텍스트 파서 경로 제거와 AI OCR 단일 경로 적용
- [x] 분석 결과의 가독성·정보 구조 개선

체크 표시는 개발과 로컬 검증 완료를 의미하며 운영 반영 완료를 의미하지 않는다.

## 공통 검증 기준

- 기존 PDF 추출 결과와 분석 기록을 계속 조회할 수 있다.
- AI OCR은 20MB·30페이지 제한, 180초 타임아웃, 일시적 오류 1회 재시도, 수동 보정, 늦은 콜백 보호를 유지한다.
- 누락된 사용량을 0원으로 표시하지 않는다. 캐시 읽기·쓰기와 모델·요금 기준을 보존한다.
- 수동 잔액 기준 시점 이후 발생한 비용만 차감하며 실제 OpenAI 잔액으로 표현하지 않는다.
- Slack 실패는 본업 결과를 롤백하지 않는다. 전송 여부가 불명확한 메시지는 자동 재전송하지 않는다.
- 요약은 원문 인용과 구분하며 자료에 없는 경력·성과를 추가하지 않는다.
- 분석 화면을 열 때 AI를 추가 호출하지 않는다.
- 업로드 → OCR → 사용량 기록 → Slack → 공고 분석 → 결과 화면의 연결을 계약·단위·격리 DB·로컬 UI로 확인한다. 실제 유료 요청과 Slack 메시지를 포함한 운영 E2E는 배포 후 별도로 검증한다.
- 계약·생성 스키마·Worker·Blog·n8n 단위 테스트, typecheck·lint·build, 격리 DB pgTAP와 offline 검증을 수행한다.

## 구현 기록

2026-10-07: 기존 코드를 확인했다. OCR은 PDF 텍스트 추출 실패 시에만 호출되고, 비용 기록은 공고 분석의 최종 성공 일부만 포함한다. 문맥 생성은 고정 문자 수로 잘라 줄바꿈을 제거한다. 기존 운영 데이터와 사용자의 변경을 보존하며 개발한다.

### 새 동작과 운영상 제한

- `/admin/usage`에서 한국 시간 기준 일별 비용·토큰과 최근 100개 호출을 조회한다. 미집계 호출은 무료로 표시하지 않으며, 다른 프로젝트·적용 이전 호출의 비용은 소급 집계하지 않는다.
- $5는 잔액 등록 폼의 초깃값일 뿐 자동 저장하지 않는다. 확인 시점 이후 **호출 시작 시각** 기준의 기록된 비용만 차감한다. 이미 실행 중이던 호출, 다른 프로젝트의 지출, 세금·실제 청구 조정은 수동 잔액 갱신 시 확인해야 한다.
- 가격은 [OpenAI 공식 가격표](https://developers.openai.com/api/docs/pricing)의 Standard 요금 스냅샷이다. 캐시 읽기·쓰기 및 긴 컨텍스트 요금을 구분하고, 미지원 모델·티어는 비용 미집계로 표시한다.
- 사용량·수동 잔액은 재정 기록이므로 문서·지원 삭제와 업무 데이터 리셋 후에도 보존한다. 원문·문서 내용은 비용 장부에 복사하지 않는다. 관리자 계정·인증은 유지한다.
- OCR 코드는 PDF 페이지 수와 전체 페이지 이미지 렌더링에만 사용한다. 모든 PDF의 텍스트 인식은 AI OCR이며 20MB·30페이지·180초 제한을 유지한다.
- 문서 등록·OCR 성공·실패 알림을 DB 트랜잭션과 함께 기록한다. 문서 삭제에는 이 알림 기록을 포함하고 전송 중이면 삭제를 차단한다.
- `/admin/notifications`에서 실패 알림과 막힌 공고 스레드를 복구한다. 확인한 상태와 현재 상태가 다르면 거절하며, 이전 시도의 늦은 callback은 새로운 시도를 완료할 수 없다. 전달 불명은 Slack에서 메시지를 직접 확인한 뒤 명시적으로 재전송한다.
- 원문 인용과 경험 요약을 구분한다. 이전 분석은 새 요약·수정 제안이 없으면 기존 강조점으로 표시한다. 새 생성 형식은 새 분석부터 적용되며 이전 결과를 자동 변경하지 않는다.
- 이번 개발에서는 운영 migration·배포·실제 유료 OCR·실제 Slack 전송·데이터 초기화를 실행하지 않는다. 로컬 UI fixture 및 격리 DB·단위 검증과 실제 운영 검증을 구분해서 보고한다.

## 최종 검증 기록

2026-10-07: 최종 코드로 `pnpm verify:offline`을 통과했다.

- 계약 32개, Worker 135개, Blog 41개, n8n·OCR·초기화 안전성 19개: 총 227개 테스트 통과.
- 폐기 가능한 별도 Supabase 환경에서 migration·DB lint·pgTAP 250개 및 생성 DB 타입 일치 확인. 운영 DB와 기존 개발 DB는 초기화하지 않았다.
- 전체 typecheck·lint·build, Workflow 정적 검증, 생성 Worker 타입·저장소 보안 검사·`git diff --check` 통과. 기존 Blog import 정렬 경고는 요청 범위 밖이라 유지했다.
- 로컬 fixture 화면에서 모바일·데스크톱 분석 배치, 원문 펼치기, 비용 그래프·미집계 표시, 전달 불명 알림의 확인 체크 및 루트 복구 UI를 확인했다. 잔액 저장·유료 AI 호출·실제 Slack 메시지는 발생시키지 않았다.
- 커밋·푸시·운영 배포는 하지 않았다. 운영 반영은 추가 DB migration → Worker → n8n Workflow·페이지 렌더링 노드 → Blog 순서이며 실제 업로드·OCR·분석·Slack 연결 검증이 남아 있다.

## 추가 운영 작업: DB migration

2026-10-07: 개발 완료 후 사용자의 별도 요청으로 운영 DB migration만 적용했다.

- 연결된 Supabase 프로젝트와 Worker 환경의 일치 및 관리자 계정을 확인하고 dry-run에서 신규 migration 3개만 미적용임을 확인했다.
- DB schema·public 데이터와 PDF 4개를 `.local/career-ops-backups/before-deploy-2026-10-07T05-33-52-783Z`에 백업했다. 백업 파일의 크기·SHA-256 및 비공개 권한을 확인했다. 이 백업의 복원 시험은 실행하지 않았다.
- `20261007010000`, `20261007020000`, `20261007030000`을 적용했다. Vault·seed·role·데이터 리셋은 실행하지 않았다.
- 적용 후 운영 DB lint 통과, 미적용 migration 0개, 새 사용량 테이블·문서 알림 컬럼 조회와 관리자 계정 보존을 확인했다.
- 기존 문서 4개·지원 1개·공고 1개·분석 1개·Slack 기록 4개·수집 기록 1개의 건수가 적용 전후 동일하다. 기존 대기 알림을 재전송하거나 과거 문서를 재추출하지 않았다.
- Worker·n8n·Blog 배포와 커밋·푸시는 아직 하지 않았다. 신규 업로드·분석은 나머지 구성요소 배포 완료 후 검증한다.
